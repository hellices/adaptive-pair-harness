## 3. 사용자 발언으로 확인한 방향

1. **실시간 양방향 페어링:** AI가 미리 전부 생성하고 사람이 나중에 검토하는 흐름이 아니다. 설계·계획·구현을 함께 진행하고, 사람과 AI가 파일 또는 여러 파일 수준에서 자연스럽게 손을 바꾼다.
2. **개인에게 맞는 참여량:** 개발자의 현재 역량과 작업 맥락에 맞춰 AI의 도움과 사람이 직접 할 부분을 조절한다. 초기에 작업 브리핑 질문으로 신호를 얻고 관찰로 보정한다.
3. **개인 프로필과 프로젝트 지식의 경계:** 개인 능력·선호는 개인 계정 스코프다. 저장소 도메인·컨벤션·아키텍처 지식은 다른 스킬·위키·하네스가 소유하고 Pair는 이를 소비한다.
4. **파일 쓰기 허용:** 이전 `no project-file writes`를 v2의 고정 제약으로 가져오지 않는다. 다만 함께 진행한다는 상호작용과 자연스러운 핸드오프가 핵심이다.
5. **여러 페어링 패턴의 경험:** 단일 고정 모드가 아니라 여러 패턴을 경험하고 상황에 맞게 전환한다. 초기 패턴 선정은 만족도·성장에 관한 실제 경험과 리서치에 근거해야 한다.
6. **main 기반의 별도 v2 브랜치:** 같은 저장소에서 새 방향으로 시작한다. 브랜치 이름 `v2/adaptive-pair`는 이미 선택·생성되었다.
7. **직전 선택은 제안서 복원:** 리서치를 기다리는 동안 Turn 10 제안서 초안을 먼저 복원하기로 했다. 이름이나 시작 브랜치를 다시 질문할 필요는 없다.

### 판단의 범위

- **확인:** 리서치는 완료되어 조용히 대기한 것이 아니라, 응답 도중 연결이 끊겼다. 이후 기존 대화에서는 재시도해도 연결 거부가 반복되었다.
- **유력한 설명:** Claude 인증·로컬 프록시 재설정 뒤 기존 대화의 연결 상태가 복구되지 않은 문제와 정황이 일치한다. 새 대화는 응답했으므로 코드 내용이나 브랜치 문제로만 설명할 상황은 아니다.
- **미확정:** 실패한 요청의 실제 목적지·이전 포트·소켓 상태는 이 기록에 없다. 오래된 프록시 주소 재사용이 정확한 원인이라고 단정할 수 없으며, 메시지에 방화벽이 언급됐다는 이유만으로 방화벽 차단을 확정할 수도 없다.
- **표시 주의:** 앞의 `(success)`가 있어도 이어지는 본문은 API 실패다. 이를 리서치 성공·정상 완료로 해석하지 않는다.

### 안전한 재개 방법

1. 현재처럼 새 대화에서 복구 문서와 v2 worktree를 사용한다. 기존 세션의 체크포인트 복원을 반복하는 것보다 확인된 진행 경로다.
2. Claude 자체의 연결 복구가 필요하면 다른 실행 중인 작업을 저장·종료한 뒤 VS Code를 완전히 재시작하고 새 Claude 대화에서 확인한다. 이 복구 작업에서는 다른 세션을 중단하거나 VS Code를 재시작하지 않았다.
3. 새 대화에서도 재현되면 발생 시각과 Claude/Agent Host 연결 로그를 보존하여 인증·프록시 경로를 조사한다. 방화벽 해제, 토큰 파일 삭제, 저장소 reset을 우선 조치로 하지 않는다.

작업 인계와 연결 장애 해결은 별개다. 여기서 작업을 이어갈 수 있지만, 기존 Claude 대화의 연결 오류가 고쳐졌다고 주장하지 않는다.

## 6. 다음 재개 순서

1. **현재 문서에서 시작:** 복구 원문·확인된 사용자 요구·후속 근거 브리프가 있다. 이전 연구의 자동 완료 알림을 기다리거나 같은 자료 복구를 반복하지 않는다.
2. **초기 패턴안 리뷰:** 공통 세션 코어에 기본 Driver/Navigator + 선택형 Guided Pairing·Ping-Pong TDD를 얹는 안의 승인을 받는다. 이는 제품 적합성 제안이지 연구 순위표가 아니다.
3. **손 바꿈 UX:** 작업 단위, 이양 제안·인수·중지, 합의된 관찰 단계의 대화·표시 방식을 구체화한다. 시각 비교가 필요할 때만 mockup을 제안한다.
4. **진입·편집 기술 가능성:** picker 진입, 실시간 사건, 편집·취소의 공식 지원 API와 배포 제약을 확인한다. 지원 여부는 아직 검증하지 않았다.
5. **상태·개인 데이터 정책:** 늦은 응답·충돌·실패 시 사용자 제어권과 개인 계정 저장·동의·접근 제어·정정·삭제를 합의한다. 저장 백엔드는 정해지지 않았다.
6. **스펙 승인 후 구현 계획:** 승인된 첫 범위를 구현용 스펙으로 정리해 리뷰받고 구현 계획으로 넘어간다. 현재 WIP는 스캐폴딩이나 구현을 시작하는 승인이 아니다.

검증 대상은 원문·33개 수집 목록 보존, 브리프 길이, 문서 링크·UTF-8·공백 오류, 두 worktree의 브랜치와 변경 범위다. v2에는 실행 코드나 테스트 설정이 없고 이번 변경은 문서뿐이므로 기존 구현의 빌드·테스트는 이 검증에 포함하지 않는다.
