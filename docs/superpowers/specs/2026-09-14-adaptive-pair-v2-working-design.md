# Adaptive Pair Harness v2 — 근거 반영 작업 설계안

**2026-09-14 / WIP / 초기 범위 검토용 / 사용자 승인 전 / 구현 미착수.**

이 문서는 [복구된 제안서 원문](2026-09-14-pair-harness-rebuild-design.md)을 대체해 과거 합의를 바꾸는 문서가 아니다. [인계 메모](../../recovery/2026-09-14-session-handoff.md)의 사용자 요구와 [근거 브리프](../../research/2026-09-14-pair-programming-evidence-brief.md)를 바탕으로 새 제안을 분리해 기록한다. 아래의 아키텍처·흐름·저장 원칙은 별도 표시가 없으면 승인 전 설계 가설이다.

## 1. 사용자 발언으로 확인된 요구

- 설계·계획·구현 전반에서 사람이 AI와 실시간으로 함께 일한다. AI가 먼저 전부 생성하고 사람이 사후 검토만 하는 경험이 아니다.
- 사람과 AI 모두 실제 파일을 편집한다. 역할 이양 단위는 의미 있는 작업이며 여러 파일을 포함할 수 있다. v1의 `no project-file writes`는 계승하지 않는다.
- 도움의 양과 사람이 직접 참여하는 방식을 개인·작업 맥락에 맞춘다. 작업 브리핑과 진행 중 관찰로 보정한다.
- 개인 능력·선호는 개인 계정 스코프다. 저장소 도메인·컨벤션·아키텍처 지식은 다른 스킬·위키·하네스가 소유하고 Pair가 소비한다.
- 여러 페어링 패턴을 경험하고 학습할 수 있어야 한다. 초기 후보는 근거와 실무 경험을 함께 검토한다.
- 같은 저장소의 main 기반 `v2/adaptive-pair`에서 새 방향으로 시작한다. 기존 구현과 이전 스펙·플랜은 보존한다.

VS Code Coding Agent picker 진입은 원하는 제품 서피스다. 해당 통합의 지원 API·배포 가능성은 아직 확인하지 않았으며, 구현 가능하다는 전제나 다른 서피스로의 변경 승인이 아니다.

## 2. 근거가 바꾸는 설계 판단

| 과거 초안의 표현 | 이번 검토의 처리 |
|---|---|
| 신입은 AI-Strong, 고수는 User-Strong이 최적 | 직접 비교 근거가 부족하다. 과제 목표·본인 선택에 따라 추천하고 고정 등급으로 강제하지 않는다. |
| 키보드를 나누면 참여·학습이 늘어난다 | 입력량과 이해는 다른 지표다. 공동 의사결정·질문·설명·디버깅도 참여로 본다. |
| Silent Observer는 항상 안티패턴 | 합의된 관찰·생각하는 시간은 허용한다. 학습 목표와 달리 이해를 놓친 상태는 별도로 확인한다. |
| Strong-Style을 그대로 AI에 적용 | 사람의 안내를 전제로 한 규칙을 그대로 옮기지 않는다. AI에 대한 즉시 질문·이의 제기·중지를 유지한다. |
| 개인 프로필은 GitHub Gist(private) | 개인 계정 경계만 확정되었다. 저장 매체·인증·접근 제어·암호화·동기화는 미결이다. |

근거의 상세 범위와 한계는 브리프의 2절을 따른다. 이번에 특정 패턴의 우월성이나 개인 실력 추론의 정확도가 입증된 것은 아니다.

## 3. 접근안 비교와 추천

| 접근안 | 장점 | 한계·비용 | 제안 |
|---|---|---|---|
| 공통 세션 코어 + 선택 가능한 세 패턴 | 여러 패턴을 경험하면서 이양·취소·편집 제어는 일관되게 유지한다. | 패턴별 안내와 전환 UX를 설계해야 한다. | **추천** |
| Driver/Navigator만 지원 | 가장 작은 범위로 자연스러운 양방향 흐름을 검증한다. | 다중 패턴 경험 요구를 초기 제품에서 충족하지 못한다. | 공통 코어의 검증 단계로만 활용 가능 |
| 능력을 자동 판정해 패턴까지 자동 배정 | 개인화 자동화라는 장기 방향과 맞는다. | 근거·동의·정확도 검증 없이 사용자의 역할과 선택을 제한할 위험이 있다. | 보류 |

추천 초기 범위는 **1인–AI, 하나의 세션·편집 제어, Driver/Navigator 기본 + Guided Pairing + Ping-Pong TDD 선택**이다. Mob, 독립적인 Expert–Expert 엔진, 자동 등급별 패턴 배정은 포함하지 않는다.

## 4. 세 패턴의 제품 동작 가설

### Driver/Navigator — 기본

현재 공동 목표를 합의하고 한쪽이 실행하는 동안 다른 쪽도 방향·가정·결과를 함께 확인한다. 대화의 발언권과 파일 편집 담당은 별개다. 어느 쪽도 Navigator가 됐다는 이유로 침묵하거나 질문을 미룰 필요가 없다.

손 바꿈은 작은 목표 완료, 막힘, 짧은 시연 필요, 명시적 인수 요청 등의 맥락에서 제안한다. 고정 타이머·타이핑 비율로 강제하지 않는다. 브레인스토밍에서는 진행을 이끄는 역할을 나눌 수 있지만, 이를 파일 편집 권한과 혼동하지 않는다.

### Guided Pairing — 선택

Strong-Style에서 착안한 AI용 변형이다. 사용자가 직접 해보고 싶으면 AI가 안내하고, 사용자가 자신의 설계 의도를 전달하려면 AI가 편집을 맡을 수 있다. 어느 쪽이 영구적인 전문가인지 등급으로 정하지 않는다.

설명 수준·힌트·시연을 상황에 맞게 조절하고, 이해가 쌓이면 지시를 줄인다. 짧은 시연 후 사용자의 직접 시도와 회고를 연결할 수 있다. 원형의 안내 신뢰·질문 지연 규칙을 강제하지 않으며, 매 턴 시험을 보게 하지 않는다. 실제 학습 효과는 검증 대상이다.

### Ping-Pong TDD — 조건부 선택

한쪽이 실패 테스트를 쓰고 다른 쪽이 통과시키며, 공동 리팩터링 후 구현한 쪽이 다음 실패 테스트를 쓴다. 사람이 테스트 작성과 구현 양쪽 역할을 경험할 수 있게 한다.

테스트 실행이 가능하고 실패 원인이 의도한 동작 차이인지 확인할 수 있을 때 선택한다. 테스트 환경 오류나 불안정한 테스트를 역할 교대 성공으로 세지 않는다. TDD가 맞지 않으면 현재 목표와 변경 내용을 유지하고 기본 모드로 돌아가는 흐름을 설계한다.

## 5. 공통 흐름과 제어 경계

1. **짧은 브리핑:** 무엇을 만들지, 어느 부분을 직접 해보고 싶은지, 낯선 지점과 시간 제약을 확인한다. 전체 역량 시험으로 만들지 않는다.
2. **현재 작업 단위 합의:** 목표·편집 범위·담당·확인 방법을 공유한다. 여러 파일을 하나의 의미 있는 단위로 묶을 수 있다.
3. **함께 진행:** AI가 담당하면 합의한 범위에서 실제 편집한다. 작업 전체를 미리 생성하거나 매 키 입력마다 허가를 요구하는 양극단을 피한다. 범위를 넓힐 때는 다시 합의한다.
4. **관찰과 제안:** 명시적 도움 요청과 작업 맥락을 우선해 다음 행동·안내 강도·손 바꿈을 제안한다. 침묵·오류 하나·어휘·커밋 개수만으로 실력이나 편집 권한을 결정하지 않는다.
5. **이양 또는 중지:** 현재 변경·검증 결과·남은 목표를 공유하고 담당을 바꾼다. 사용자의 중지·인수 요청이 자동 제안보다 우선한다.
6. **짧은 마무리:** 이해한 것·남은 것·다음 출발점을 함께 확인한다. 개인 프로필에 남길 요약은 사용자가 검토·정정할 수 있게 하는 안을 제안한다.

안전 불변조건 제안:

- 같은 편집 범위에서 사용자와 AI가 충돌하는 변경을 조용히 덮어쓰지 않는다. 사용자의 편집을 잠그는 대신 AI 적용을 멈추고 상태를 다시 맞춘다.
- 중지·인수 이후 도착한 AI 결과는 현재 파일에 자동 적용하지 않는다. 이미 적용된 변경을 자동 삭제하지 않고 적용 여부와 남은 차이를 보여 준다.
- 연결 실패 시 모델 응답·도구 실행·파일 적용을 같은 성공으로 취급하지 않는다. 완료가 확인되지 않은 상태 변경 작업은 자동 재실행하지 않는다.
- 재개 시 마지막 공동 목표와 실제 파일 상태를 대조한다. AI 편집을 계속할지 다시 확인한다.

이 항목들은 요구할 동작이지 이미 구현된 보장이 아니다. 정확한 상태 전이·취소 경계·충돌 검출은 다음 설계 주제다.

## 6. 책임 분리 제안

| 구성 | 책임 | 경계 |
|---|---|---|
| 공통 세션 코어 | 공동 목표, 현재 작업, 담당, 패턴, 이양·중지·재개 상태 | UI나 개인 저장 서비스에 종속시키지 않는다. |
| 패턴 정책 | 현재 모드의 안내와 다음 행동·교대 제안 | 직접 파일을 쓰거나 사용자 중지를 무효화하지 않는다. |
| 호스트·편집 어댑터 | 에디터 사건, 버전 확인, 허용된 편집·취소·결과 표시 | VS Code에서 실제 가능한 수단을 먼저 확인한다. |
| 개인화·프로필 경계 | 본인이 선택한 선호와 제한적인 관찰 요약을 추천에 사용 | 불확실성을 표시하고 열람·정정·삭제를 제공한다. 저장 방식은 미결이다. |
| 프로젝트 지식 소비 경계 | 외부 스킬·위키·하네스의 관련 맥락을 읽는다. | 개인 실력 프로필이나 프로젝트 지식 저장소를 대신 소유하지 않는다. |

영속적인 개인 프로필을 학습한 모델처럼 표현하지 않는다. 작업·언어별 익숙도와 선호에 대한 수정 가능한 가설로 다룬다. 초기 프로토타입은 영속 저장 없이 세션 내 선호로 검증하는 안도 가능하지만, 이는 최종 개인 계정 요구를 없애는 결정은 아니다.

원격 개인 프로필에는 원본 코드·경로·진단·대화·비밀 정보를 넣지 않는 방향을 제안한다. 모델이 작업을 위해 소비할 컨텍스트의 전송 정책은 개인 프로필 저장 정책과 별도로 정해야 한다. GitHub 이력 수집은 승인된 기본 동작이 아니며, 인증된 개인 저장소와 secret Gist를 같은 것으로 가정하지 않는다.

## 7. 검증할 제품 가설

| 질문 | 확인 방법 제안 | 피할 대리 지표 |
|---|---|---|
| 함께 진행한다는 느낌과 주도권이 있는가? | 종료 시 짧은 피드백, 원치 않은 개입·이양·중지 사례 확인 | 교대 횟수만으로 만족도 판정 |
| 사용자의 이해·성장이 유지되는가? | 동의한 짧은 설명·변형·디버깅, 필요 시 후속 독립 과제 | 타이핑 비율, AI의 실력 점수, 즉시 자신감만 사용 |
| 작업 결과가 유효하고 비용이 수용 가능한가? | 결과 품질·검증 결과·총 소요 시간·피로를 분리 | 속도 하나로 모든 효과 판단 |
| 인수·중지·재개가 신뢰할 만한가? | 지연 응답, 편집 충돌, 중복 사건, 재연결 시나리오 | 대화상 완료 문구를 파일 적용 증거로 사용 |

이는 향후 사용자 시험·구현 테스트의 방향이며, 현재 실행하거나 통과한 테스트가 아니다. 이번 작업은 문서만 변경한다.

## 8. 다음에 결정할 순서

1. **초기 패턴 구성 승인:** 기본 Driver/Navigator와 선택형 Guided·TDD를 함께 가져갈지 확인한다. 이번 리뷰 질문은 이 범위에 한정한다.
2. **손 바꿈 UX:** 작업 단위의 합의·제안·인수·중지·관찰 단계가 대화와 에디터에 어떻게 나타나는지 구체화한다. 시각 비교가 필요해지는 시점에만 mockup을 제안한다.
3. **통합 가능성:** picker 진입, 실시간 사건, 편집·취소 수단의 공식 지원과 배포 제약을 조사한다. 불가능한 부분이 있으면 대안을 별도 승인받는다.
4. **상태·데이터 정책:** 늦은 응답·동시 편집·재연결 상태 전이, 개인 계정 저장·동의·보존·삭제 정책을 확정한다.
5. **스펙 리뷰 후 구현 계획:** 승인된 첫 범위를 구현용 스펙으로 정리하고 계획을 작성한다. 이 WIP, 복구 원문, v1 계획 어느 것도 구현 시작 승인이 아니다.
